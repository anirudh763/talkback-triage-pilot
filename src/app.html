    Research methods
    
    
    
    
    The question: when an Android accessibility bug report includes TalkBack reproduction steps and the app version, does an AI judge differently whether a developer could start reproducing it? And do people agree with its judgments?
    
  
    
  
    
    
      
      
    1. Collect real reports
      Public GitHub issues from two open-source Android apps, fetched on 9 November 2026. WordPress for Android: issues labelled Accessibility that mention TalkBack or a screen reader (51). AntennaPod: every issue labelled Area: Accessibility (24). Images and videos become [image] and [video], template checklists are dropped, and bodies are cut at about 1,200 characters.
      2. 
      
    2. Check each report
      Pattern rules flag six details: TalkBack reproduction steps, app version, Android version or device, expected vs. actual behaviour, what TalkBack said, and a recording or screenshot. The rules are deterministic, so anyone can rerun them.
      3. 
      
    3. Make controlled copies
      "TalkBack steps removed" drops only the action steps: the steps heading and the list items under it. It keeps steps that report what happened (for example "Notice it crashes"), anything TalkBack said, recordings, notes, workarounds and "Tested on" lines. "Version removed" drops the app version, Android version, device and app source. Each copy is checked: if the checker sees that any other detail was lost, that copy is not run. Every removal is listed line by line in results/pair_review.md, and the report view shows it with strike-through. This check is automated pattern matching: it confirms the other measured details are still there, not that nothing else changed in meaning. Two known cases: WordPress-Android #21127's copy without steps still has a sentence that describes how to reproduce the bug ("When Talkback is enabled, scrolling to a page where the remove button is offscreen..."), and AntennaPod #8145's copy drops a step that reports what happened ("Screens auto advance without a next/previous").
      4. 
      
    4. Ask Claude about each copy
      Each copy goes to Claude in its own call with the same instructions. Claude answers two questions: could a developer start reproducing this with the information here, and could a TalkBack user finish the task. It also says what is missing. No confidence score is shown, because a model's self-reported confidence isn't calibrated.
      5. 
      
    5. Compare, then check against people
      The pilot counts how often Claude's answer changes between a report and its shortened copy, with an exact McNemar test on the pairs. People label reports on the Labels screen, blind to Claude's answers, using the same rubric. Each version is scored only against labels of that same version. A simple checklist rule (enough to start reproducing when the text has steps) is scored the same way, to see whether Claude adds anything over the checklist.
      6. 
    
    
  
    
  
    
    
    
      
    What the results can and can't show
    
      
      
        
    • The removal comparison shows whether Claude's answer depends on those lines. It doesn't show that Claude is right.
      • 
        
    • The "clean copy" check is automated. It doesn't prove a copy differs only in the removed detail; see WordPress-Android #21127 and AntennaPod #8145 above.
      • 
        
    • Whether Claude is right needs two people labelling independently. Start with five reports, compare, tighten the rubric, then label more.
      • 
        
    • Many WordPress issues were written by the app team as audits, not by end users. Report the two apps separately.
      • 
        
    • Model answers vary between runs. Repeat runs, and keep the model setting fixed within a comparison.
      • 
        
    • Nothing here shows yet that the app improves triage or helps developers reproduce bugs.
      • 
        
    • GitHub outcomes (closed, not planned, still open) are context only.
